# Part 00 — Gates and Design Decisions
# Task: Implement the SMTP Relay (smtp.orbit.devotel.io)

> Scope of this part: context, the ten design decisions, architecture and deployment shape, the blocking verification gates (G1–G4), backend dependencies, and the master "Done when" acceptance list.
> Implementation detail lives in [01-relay-core.md](01-relay-core.md); panel work in [02-panel.md](02-panel.md); webhook contract in [03-webhooks.md](03-webhooks.md); documentation changes in [04-docs.md](04-docs.md).

## Why

Today, the only way to send email through Orbit is the HTTP endpoint (`POST /api/v1/messages/email`):

- A whole class of sending systems — CRMs with built-in SMTP notifications, POS software, monitoring tools, ERPs — can only emit email over SMTP. For them, integration means a rewrite or a third-party relay.
- The SMTP relay is already **documented and advertised**: `smtp.orbit.devotel.io`, ports 587/465/2525, the `apikey` sentinel username, six client-library snippets. Developers who follow the docs hit `NXDOMAIN` at the DNS step — the platform looks broken before the first command runs.
- The docs page carries a "has not launched yet" callout admitting the gap, so this is a known, shipped-as-spec feature waiting for an implementation — not a new idea.

Implementing the relay closes the documented gap, unblocks legacy senders, and turns the docs from describing a ghost into describing reality.

## Design decisions (what we're building)

An authenticated SMTP ingress edge that submits into the same email pipeline as the HTTP send endpoint — same API key, same rules, one ingress added:

1. **DNS + edge hostname.** `smtp.orbit.devotel.io` resolves publicly; the edge listens on `587` (STARTTLS, recommended), `465` (implicit TLS), `2525` (STARTTLS alternate). TLS is required on every port. AUTH on a plaintext session is refused with `530 Must issue a STARTTLS command first` — never a 3xx reply, which a compliant client reads as "send your credentials now." After STARTTLS the client re-issues EHLO before AUTH.
2. **API-key authentication.** Username is the literal sentinel `apikey`; the password is an active tenant API key. Permanent credential failures — wrong username, revoked key, stale secret — return a single `535`. A temporarily unavailable key-lookup backend returns `454` (temporary): a `535` there would tell clients their credentials are permanently bad and stop them retrying. Key rotation/revocation under **Developer → API Keys** applies immediately, with no service restart: the revocation event **closes live authenticated sessions** (`421`) and invalidates the edge's cached validation; as a consistency fallback, every `MAIL FROM` on an open session re-validates the key, so a session can never keep sending after its key is revoked (SMTP sessions carry many messages — "next AUTH" alone is not enough). No separate SMTP credential exists.
3. **Message integrity — the payload is content-preserving, not byte-identical.** The relay stores and submits; it never rewrites the sender's content. All sender-authored headers, the MIME tree structure, part boundaries, encodings, and body bytes survive unchanged — DKIM signatures still verify at the receiving side, S/MIME and PGP signed parts stay intact, calendar invites survive, and headers such as `List-Unsubscribe` are never dropped. Custom `X-` headers stay in the message — "ignored" means only that they don't become contact fields. The `Bcc:` header is removed before storage and outbound, so envelope-only recipients can never leak through a header. The exact keep-vs-add boundary (the closed list of permitted transformations) is defined in the implementation section — anything not on that list is forbidden. The HTML part is preferred **for the stored message record's body only** (matching HTTP selection). An empty or unparseable body is refused with `554` as an explicit Orbit product rule (SMTP itself permits an empty body).
4. **Shared pipeline, not a side door.** Submissions enter the same email pillar as HTTP sends: suppression and consent gates, verified-sender checks, billing, delivery tracking, and the shared per-tenant rate pool (default 200 msg/min) all apply. Rate-pool exhaustion answers `451 4.7.1` — temporary, inviting retry — decided **before the message body is uploaded**; a transaction that can never fit the tenant's pool is refused permanently `552 5.7.28` (retrying cannot succeed), and **admission is atomic per transaction** with a fairness rule so large transactions are not starved by small ones: if the pool cannot accommodate every surviving recipient, the whole transaction is refused before acceptance, never a subset (see Durable acceptance). Refused messages consume no quota. Connection-level flood protection closes abusive sessions.
5. **Envelope sender handling.** `MAIL FROM` (envelope) and `From:` (header) are distinct identities. The `From:` header is validated against the tenant's verified senders exactly as on HTTP — an envelope-verified `MAIL FROM` never substitutes for a verified `From:`. The client's `MAIL FROM` is **stored as traceability metadata and never used on the wire**: bounce correlation runs through Orbit's own controlled VERP return-path identifier, so bounces return to Orbit (delivery tracking and suppression stay complete) and SPF checks pass for the sending infrastructure.
6. **Durable acceptance, decided per recipient at RCPT TO.** Per-recipient decisions happen at `RCPT TO`, where the client can observe them: a suppressed recipient is refused with `550` (the tenant is already known after AUTH); a recipient over the transaction cap with `452 4.5.3`. **Recipient-specific consent is in the same class, stated as a two-part rule:** (a) a successful `RCPT TO` reply means **all** recipient-specific eligibility checks — suppression, consent requirements, any future recipient-level gate — have **passed** for that recipient; (b) if a required recipient-specific check **cannot be evaluated at `RCPT TO`**, the transaction must not proceed to durable acceptance: it is rejected in full before `250`, with the documented temporary or permanent reply appropriate to the reason. **Message-level consent (marketing vs. transactional) cannot be known at RCPT TO** — the message type lives in the content/headers, not the envelope — so it is a **transaction-level gate evaluated after `DATA`, before the `250`**: a consent failure refuses the *whole* transaction (permanent or temporary per the reason), never a subset of recipients; the no-post-DATA-drop rule is preserved because nothing was ever accepted. **Duplicate envelope recipients are deduplicated:** repeated `RCPT TO` for the same address in one transaction answers `250` but creates **one** record and bills **one** unit — the duplicate is a no-op, not a second billed recipient (per-recipient fanout counts distinct surviving addresses). **No recipient may be silently dropped after `DATA`**. After `DATA`, `250` means **every surviving envelope recipient is accepted** — nothing accepted is dropped after the fact. If *zero* recipients survived, the transaction is dead on arrival: the client's `DATA` is answered `554` (refused — no message is created, nothing is persisted, nothing is billed). **One message record per surviving (distinct) recipient** is created — the same fanout model the HTTP path uses for multi-recipient sends (its 207 multi-status response carries one row per dispatched recipient) — and the records are durably persisted via the outbox pattern *before* the `250` is written to the socket; after `250`, Orbit owns delivery asynchronously, exactly like the HTTP path's `202 queued`.
7. **Security and resource limits (v1, not future hardening).** Anonymous relay disabled — unauthenticated transactions are rejected. Bare-LF line endings in commands and DATA are rejected (SMTP smuggling); any plaintext commands buffered before STARTTLS completed are discarded (command injection). Global and per-IP connection limits, authentication attempt throttling, idle/command timeouts, bounded concurrent sessions. Explicit maximums for message size, MIME nesting depth, header size, and attachment count; a per-transaction recipient cap of **at least 100 (RFC 5321)**; MIME parsing is resource-capped so malformed or pathological messages can't exhaust the edge. API keys and credentials are never logged.
8. **Protocol completeness.** EHLO advertises `SIZE 26214400` **with the exact octet maximum** (so clients can pre-check message size instead of uploading first), `8BITMIME`, `PIPELINING`, and `ENHANCEDSTATUSCODES` on the plaintext session; **`AUTH PLAIN LOGIN` is advertised only on the post-STARTTLS session** (RFC 4954 — password mechanisms never on plaintext). `SMTPUTF8` is an open decision tied to internationalized-address support. `RSET` and `NOOP` are supported; multiple transactions per connection are allowed; a null sender (`MAIL FROM:<>`) is accepted as valid; every accepted message gets a `Received:` trace header.
9. **Documentation to match.** Where the current docs contradict the SMTP protocol, fix the docs — the protocol wins: the `335` reply becomes `530` (334 is the actual SASL challenge code), and the mixed-recipient fanout example is rewritten to the RCPT-TO refusal model — the "(1/2 recipients)" post-DATA drop cannot stand, because clients never parse reply text and treat an accepted transaction as delivered. When live, remove the "not launched yet" callout. → detailed change list in [04-docs.md](04-docs.md).
10. **Panel surface.** The existing **Developer → SMTP page stays the single SMTP surface** — launch upgrades it with the enable/disable toggle, a usage panel, and domain-status links; no duplicate SMTP tab is added to the Email channel page. The message record gains an `ingress` field (`api` | `smtp`) surfaced as a badge + source filter in the Email message list. SMTP authentication updates the API key's Last Used timestamp like API calls do. No new credential entity, no new "connections" page. → detailed UI plan in [02-panel.md](02-panel.md).

## Architecture

Two ingress adapters, one business-logic entry point:

| Layer | Responsibility |
|---|---|
| Ingress adapters | HTTP REST controller · SMTP edge (protocol, TLS, AUTH, parsing, reply-code translation) |
| Shared email application service | Auth context · validation · suppression · consent · billing · rate limiting · persistence · delivery |
| Existing delivery pipeline | Queues · providers · tracking · logs (asynchronous delivery) |

The SMTP adapter owns **only**: SMTP protocol, TLS, AUTH mechanics, parsing, mapping the session into an application-level request, and translating application results into SMTP reply codes. Every business rule (suppression, consent, sender verification, billing, quota) stays in the shared service, so a rule change never updates two implementations.

**Deployment shape** (final choice after examining the backend repo):

| Approach | Advantages | Disadvantages |
|---|---|---|
| Dedicated SMTP edge service, internal API into the app | Protocol handling isolated; scales and restarts independently; app stays request/response | One more service to deploy, monitor, secure internally |
| In-process SMTP listener in the app | No new service; direct access to app services | Long-lived TCP sessions inside a request/response runtime; couples deploys; restarts drop sessions |
| Mature SMTP server (Postfix/Haraka-like) with custom auth + pickup hook | Battle-tested protocol handling | Customization and integration constraints; two config surfaces |

Recommendation: **dedicated edge service** talking to the application through an internal authenticated interface — it keeps protocol handling independent of the HTTP app while both share business logic. Do not lock the library choice until the repo answers the open decisions below.

**Open decisions to resolve against the real backend:**

1. Edge technology/library for the chosen stack (protocol parsing + TLS + AUTH only — no business logic in it).
2. How AUTH validates API keys: internal authenticated call, shared credential cache, or direct key-hash lookup — and cache invalidation so revocation applies on the next attempt.
3. How submissions enter the pipeline: internal HTTP call, queue/job insert, or outbox write (persistence must be durably committed before `250`).
4. Deployment topology: where the edge runs, how traffic reaches it, restart policy.
5. Monitoring: metrics, alerting, health checks, restart/draining model.
6. Whether the email channel supports internationalized addresses — decides if `SMTPUTF8` is advertised.

## Pre-implementation verification gates (blocking — implementation of the affected sections starts only after these pass)

These gates are **engineering verification responsibilities owned by the implementation team** — the planning agent has no backend or infrastructure access, so the backend/infrastructure engineers who do must execute them and record the deliverables:

- **G1 — Transformation enumeration, MIME-representation proof, and raw-passthrough feasibility.** Audit the backend send path and reconcile every send-time transformation against the preservation-boundary table (stages 1–10). Additionally, **demonstrate that the original RFC 5322/MIME representation survives the pipeline unchanged outside the allowed transformations** — validation and parsing must operate on a copy, never re-serialize a reconstructed message into the send path. **Critical feasibility question: the HTTP path builds mail from structured fields; SMTP carries the sender's original bytes.** Determine how the existing providers are wired — API-based providers (SES, Mailgun, Resend-style) may not accept a raw RFC 5322 message with Orbit-controlled envelope and signature, in which case byte-passthrough is impossible or a major rebuild, and the honest outcomes are: (a) raw passthrough is supported for SMTP-protocol providers / raw-send provider modes, or (b) the preservation boundary is re-scoped for API providers to "content-preserving, not byte-identical" with the re-scoped guarantee documented per provider. The gate decides; the plan's integrity promises bind only to what G1 proves deliverable. If the pipeline cannot demonstrate byte-preserving MIME handling, that is a required backend change. Deliverables: the reconciled table + the MIME-preservation demonstration + the per-provider raw-send feasibility verdict. If extra transformations exist, each is added with content-altering classification and gating, or disabled for SMTP-originated messages. **Blocks:** all integrity work.
- **G2 — Test-mode webhook capture.** With a `dv_test_sk_` key, submit a real HTTP email send in a sandbox tenant and record which webhook events fire (expected per the Test-mode event table in [03-webhooks.md](03-webhooks.md): none beyond the HTTP baseline; if the sent stage fires a test-specific event, capture its shape). Deliverable: the confirmed event table. **Blocks:** webhook fan-out work for SMTP.
- **G3 — Return-Path target verification.** Identify the actual Domain-Setup Return-Path CNAME target host and verify its zone: SPF record authorizing Orbit's sending IPs, and MX records routing bounce traffic back to Orbit. Deliverable: the concrete target hostname + DNS proof (zone dump + a live SPF evaluation). **Blocks:** the envelope/return-path implementation and the bounce-loop tests.
- **G4 — Concurrent oversubscription proof.** Design the atomic reservation mechanism (see Rate limits in [01-relay-core.md](01-relay-core.md)) and demonstrate under load that parallel HTTP and SMTP submissions racing the pool boundary cannot oversubscribe it — no partial accepts, no quota over-consumption. Deliverable: the reservation design (including the fairness/aging rule — no starvation) + a concurrency proof/test run. **Blocks:** rate-admission implementation.

2. Messaging → Write scope description text covering SMTP — copy change.
3. Developer → SMTP page upgrades (toggle, usage panel, domain-status links) — panel work.
4. Outbound bounce address (VERP-style Return-Path) for SMTP-created messages — likely already exists for HTTP sends; confirm and reuse (G3 covers the DNS side).
5. `test_sent` terminal status and test-mode routing for SMTP-created records (key-prefix rule, no provider call, no billing) — confirm the pipeline treats SMTP-created test messages identically to HTTP test sends (G2 covers the webhook side).

7. SMTP session/transaction logs and the usage-panel counters — new observability work.

## Done when (master acceptance list — the single source for launch acceptance)

- **Release gate (external connectivity and TLS).** From a vantage point *outside* Orbit's network: `smtp.orbit.devotel.io` resolves through public DNS (verified against `8.8.8.8` and `1.1.1.1`); TCP connects on 587, 465, and 2525; the TLS certificate on every port is valid, unexpired, and matches `smtp.orbit.devotel.io`; STARTTLS negotiation succeeds on 587 and 2525, and implicit TLS completes on 465; the post-STARTTLS EHLO advertises exactly `AUTH PLAIN LOGIN` (plaintext EHLO advertises none of the password mechanisms) and `SIZE 26214400`. Launch is blocked while any check fails.
- **Return-Path DNS verified as a testable criterion (G3 exit test):** the Domain-Setup Return-Path CNAME target is confirmed — its zone carries an SPF record authorizing Orbit's sending IPs, and bounce MX routing points back to Orbit — proven live by sending an SMTP message to a deliberately undeliverable remote address and confirming the bounce reaches Orbit's bounce MX, marks the record `message.failed`, and fires the webhook.
- STARTTLS → EHLO → AUTH → submission works end-to-end as documented; `swaks` and `openssl s_client` probes pass, and the six client snippets in the docs run verbatim.
- AUTH before STARTTLS gets `530`; permanent credential failures get a single `535`; a down key-lookup backend gets `454`; a revoked key fails the next SMTP authentication attempt with no service restart — **and closes every live session already authenticated with that key (`421`), with per-`MAIL FROM` re-validation as the fallback**; a session authenticated with a live key keeps working across multiple transactions.
- A suppressed recipient is refused at `RCPT TO` with `550`; **consent and every recipient-specific eligibility check resolves before the RCPT TO reply** — no recipient is ever dropped after `DATA`; an over-cap recipient with `452 4.5.3`; after `DATA`, `250` means every surviving envelope recipient is accepted.
- **Rate-pool admission is atomic**: a transaction the pool cannot currently accommodate is refused `451 4.7.1` before the body upload and before acceptance — never a subset accept — and a refused transaction consumes no quota; a transaction that can **never** fit the pool is refused permanently `552 5.7.28`; a repeatedly refused large transaction is not starved by a stream of smaller ones (fairness rule holds under load).
- A DKIM-signed submission still verifies at the receiving side; S/MIME/PGP parts and calendar invites arrive intact; the `Bcc:` header is stripped; `List-Unsubscribe` and custom `X-` headers are preserved.
- A message is durably persisted before its `250` — an edge crash immediately after `250` never loses an accepted message — and **each surviving recipient produces its own message record** (the HTTP multi-recipient fanout model), persisted before the `250`.
- **The original RFC 5322/MIME representation flows through the pipeline unchanged outside the allowed transformation stages** — demonstrated per gate G1 (parse-as-copy; no reconstruction or normalization in the send path).
- The sender's content survives the relay under the closed preservation boundary — **only the stages in the reconciled transformation table (1–10) are ever applied, verified by header diff** — and client signatures behave per the per-family guarantee (DKIM `h=`/body-hash semantics; S/MIME/PGP content-octet semantics; tracking is the only content-altering gate); DATA with zero surviving recipients is refused `554` with nothing created or billed; a test-key submission answers a normal `250` and terminates at `test_sent` with no provider call and no billing, firing exactly the webhooks HTTP test sends fire (per gate G2's confirmed table).
- An unverified `From:` is rejected exactly as on HTTP; the client `MAIL FROM` is stored but Orbit's controlled bounce address is what goes on the wire.
- Attachment-carrying submissions produce the same message record as the HTTP equivalent.
- Rate-pool exhaustion answers `451 4.7.1` and refused messages consume no quota.
- Security limits hold: no anonymous relay, bare-LF input rejected, plaintext buffered behind STARTTLS discarded, per-IP connection caps, and oversized/pathological MIME is rejected without resource exhaustion.
- Relayed messages appear in the same message records/logs as HTTP sends, billed to the authenticating key, drawing from the same rate pool.
- The Channels grid still shows exactly one Email card, and the Email channel page gains only the Sending-authentication cross-link — no SMTP tab exists there.
- SMTP-originated messages carry an `ingress` badge in the Email message list and are filterable by source (All / API / SMTP).
- SMTP authentication updates the API key's Last Used timestamp and IP exactly like API calls.
- A submission with a missing From: header falls back to the tenant's From-email defaults; an unverified From: domain is refused `554` with a pointer to the domain card; a tenant with the relay disabled gets `554 5.7.1` at MAIL FROM.
- A custom-domain customer publishes only the four standard Domain-Setup records (DKIM / SPF / DMARC / Return-Path) — no SMTP-specific records exist; the Developer → SMTP page links to domain-verification status with traffic lights.
- The Developer → SMTP page remains the single SMTP surface (connection profile, auth card, test command, toggle, usage panel) — no duplicate SMTP tab on the Email channel page; the Email page links to it from Sending authentication.
- Every existing email webhook event fires identically for **live** SMTP-originated messages and for **live** HTTP sends, with payloads carrying `ingress`; **no new event types are introduced**; protocol-level rejections (550/452/501/535/454/451/421/554) fire no webhooks; bounces of SMTP mail surface as `message.failed` via the VERP return-path.
- Test-mode (`dv_test_sk_…`) SMTP submissions produce **exactly the same webhook behavior as HTTP test-mode sends, event-for-event** (per the test-mode event table in [03-webhooks.md](03-webhooks.md), confirmed against the backend implementation).

Every acceptance criterion above must trace to at least one test in the master test matrix ([01-relay-core.md](01-relay-core.md)).
